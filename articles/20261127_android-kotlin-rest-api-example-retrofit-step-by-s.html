Android Kotlin REST API Example: Retrofit Step by Step

More than 60% of professional Android developers use Kotlin, and 95% of the top 1,000 Android applications contain Kotlin code, according to Android Developers. On the server side, REST was used by 93% of API developer teams as an API architectural style in 2025, according to an analysis citing Postman's State of the API Report. That combination makes a solid Android Kotlin REST API example the baseline skill for almost every mobile team.

Most tutorials stop the moment one GET request prints a JSON object to Logcat. Production networking falls apart right after that point. Rotating a phone mid-request, losing cellular signal during a 300 MB dashcam upload, or letting ten parallel requests trigger ten token refreshes at once will break a naive client on day one.

Building a dependable client means owning screen state, canceling stale coroutines, enforcing strict retry rules, and streaming large Multimodal Video and Multimodal Audio captures from phones, smart glasses, GoPros, dashcams, CCTV hubs, and robots without crashing the heap.

What You Will Build and Why Kotlin Fits

In 2025, 8.1 million developers worldwide had Kotlin experience, according to JetBrains' State of Kotlin report. Writing your networking layer in Kotlin aligns directly with how modern Android teams structure asynchronous code, immutable data models, and UI state.

Consider a concrete scenario: you're building an Android companion app that searches a REST backend for timestamped video and audio moments, uploads fresh recordings from a connected camera, and polls an asynchronous processing job while the user walks across a spotty LTE connection. Firing a single HTTP call takes ten lines of code. Keeping that screen responsive and predictable when the network drops takes careful architecture.

Four Layers That Keep Networking Maintainable

Rather than dumping HTTP code into an Activity or composable, split the client into four focused responsibilities:

  • Retrofit turns REST endpoints into typed Kotlin interfaces with @GET, @POST, and @Multipart annotations.
  • OkHttp handles the actual sockets, TLS handshakes, connection pooling, timeouts, and request interceptors.
  • Kotlin Coroutines push blocking I/O off the main thread and tie request lifecycles to structured cancellation.
  • Lifecycle ViewModel holds a sealed UI state across screen rotations so your composables only render what's ready.

By the end of this walkthrough, you'll have a compiling Kotlin architecture with a repository boundary, a sealed SearchUiState, mapped HTTP error handling, a single-flight token interceptor, and chunked media upload support. If you already have Retrofit wired up, jump straight to the state pipeline, error matrix, or camera upload patterns below.

Project Setup and a Working Retrofit Client

A clean Android Kotlin REST API example starts by keeping your dependency list tight. Every library in the request path needs a clear job, and anything that prints request headers or payloads must stay out of release builds.

Core Dependencies and When to Include Them

Library Role in the example Add when
Retrofit Declares endpoints as typed Kotlin interfaces Always
OkHttp HTTP engine for timeouts, interceptors and connection reuse Always, Retrofit uses it
JSON converter (kotlinx.serialization or Moshi) Turns JSON into data classes and back Always
kotlinx-coroutines Suspend calls that stay off the main thread Always
Logging interceptor Prints request and response details Debug builds only
Lifecycle ViewModel Keeps request state across rotation Any screen that shows network data

I recommend picking kotlinx.serialization or Moshi over older reflection-heavy converters on new Kotlin projects. Both respect Kotlin nullability rules cleanly, so a missing required JSON field fails fast at the network boundary instead of throwing a surprise NullPointerException three screens later.

Six Steps to a Compiling Retrofit Client

  1. Declare internet permission in AndroidManifest.xml. Add <uses-permission android:name="android.permission.INTERNET" /> above the <application> tag. Android grants this at install time without a runtime dialog, and omitting it causes every socket call to fail immediately before leaving the device.
  2. Add dependencies to your Gradle version catalog. Pin the latest stable releases of Retrofit, OkHttp, your chosen JSON converter, kotlinx-coroutines-android, and lifecycle-viewmodel-ktx inside libs.versions.toml, then wire them into your app module's build.gradle.kts.
  3. Define explicit serializable data models. Create SearchResponse wrapping a List<SearchItem>, where each SearchItem exposes id: String, title: String, startSeconds: Double, and endSeconds: Double. Add UploadResponse(val jobId: String, val status: String) and JobStatusResponse(val jobId: String, val state: String) so every backend key maps to a typed property. Use nullable types only when the backend omits a field.
  4. Declare your endpoints in one Retrofit interface. Mark every function suspend so Retrofit dispatches calls asynchronously without blocking the caller. A single service interface can hold both text queries and media transfers: @GET("search") suspend fun search(@Query("q") query: String): SearchResponse, @Multipart @POST("uploads") suspend fun upload(@Part file: MultipartBody.Part): UploadResponse, and @GET("jobs/{id}") suspend fun getJobStatus(@Path("id") jobId: String): JobStatusResponse.
  5. Configure a single shared OkHttpClient. Build one client instance and inject it everywhere so connections stay pooled. Set separate timeouts: keep connectTimeout and readTimeout tight (for example, 15 seconds and 30 seconds) so dead sockets fail quickly, but set writeTimeout longer (for example, 120 seconds) to give large camera uploads room on slow uplinks. Attach an auth Interceptor that reads the bearer token from encrypted storage (EncryptedSharedPreferences or Keystore-backed DataStore) and adds Authorization: Bearer $token. Attach HttpLoggingInterceptor only inside an if (BuildConfig.DEBUG) guard.
  6. Build one Retrofit singleton from BuildConfig. Pass your OkHttpClient, attach the JSON converter factory, and call .baseUrl(BuildConfig.API_BASE_URL) with a guaranteed trailing slash. Keeping the base URL in build flavor configuration lets you switch between staging and production without touching feature code.

Security rule: Never attach HttpLoggingInterceptor at Level.BODY or Level.HEADERS in a release build. Any log aggregator or user bug report will capture bearer tokens, signed media URLs, and private query text straight from Logcat.

Verifying Your First Staging Call

Before building any screens, verify the transport layer in isolation. Point BuildConfig.API_BASE_URL at your staging server, invoke apiService.search("loading dock") from a temporary coroutine or instrumentation test, and inspect the debug output.

Your checkpoint is simple: the project compiles with zero warnings, the staging server returns a 200 OK, and Logcat displays a parsed list of SearchItem objects with intact startSeconds and endSeconds values.

Wiring the Repository to ViewModel and UI State

Getting JSON back from staging is the straightforward part. Android's network connectivity documentation describes Retrofit as a type-safe HTTP client built on OkHttp, recommends placing calls behind a repository to avoid duplication, and requires keeping network work off the main thread via withContext(Dispatchers.IO) or an injected dispatcher. It also stresses transmitting traffic over SSL and minimizing sensitive data over the wire, making HTTPS and redacted logs essential for mobile media and robotics telemetry.

That layering matches Android's data layer architecture guide, which recommends main-safe data sources, suspend functions for one-shot operations, and Flow for observable state. Follow a strict build pipeline from the bottom up: serializable DTO models, the Retrofit interface, the configured OkHttpClient and Retrofit instance, a repository, a ViewModel, and finally your Compose UI.

Separating Transport Models from Screen State

The repository should be the only class in your codebase that imports Retrofit. Expose a clean contract such as suspend fun search(query: String): Result<List<SearchItem>> and wrap the network execution inside withContext(ioDispatcher) (defaulting to Dispatchers.IO) so any caller can invoke it safely from the main thread. Inside that block, convert raw transport DTOs into domain models and catch HTTP or serialization failures before returning.

In the ViewModel, model every screen state explicitly with a sealed hierarchy called SearchUiState:

  • Idle: The initial screen before the user enters a query.
  • Loading: An active search request is in flight.
  • Empty: The backend returned 200 OK, but zero timestamped clips matched.
  • Content(val items: List<SearchItem>): Validated results ready to render.
  • Error(val message: String, val canRetry: Boolean): A mapped failure telling the UI whether a Retry button makes sense.

Preventing Search Race Conditions

Typing into a search bar exposes a subtle bug that breaks many first implementations. If a user types "red" and then quickly finishes typing "red truck", the first request can stall on a slow cell tower and arrive after the second response, overwriting the newer "red truck" results with stale data.

Lock down the search flow with four concrete steps:

  1. Debounce user input by roughly 300 ms using Flow.debounce(300) or a delayed coroutine so rapid keystrokes don't hammer the backend.
  2. Cancel the previous search Job before starting a new one (or switch via flatMapLatest), guaranteeing that only the latest query can write to SearchUiState.
  3. Transition to Loading, call repository.search(query), and map the Result cleanly into Content, Empty, or Error.
  4. Expose state as StateFlow<SearchUiState> and collect it in Jetpack Compose with collectAsStateWithLifecycle(), which automatically pauses collection when the screen drops into the background.

Keep these production guardrails in place as your app grows:

  • Never leak DTOs into composables: When the backend renames a JSON property, only your mapper should change, not five UI files.
  • Keep CancellationException out of Error state: If you write catch (e: Exception) inside a repository, rethrow CancellationException immediately so canceled searches don't flash false error banners.
  • Don't restart calls on configuration changes: Let the ViewModel own the coroutine in viewModelScope rather than launching requests from a composable LaunchedEffect keyed on ephemeral UI state.
  • Instrument transport metrics at the repository layer: Track request latency, retry counts, bytes transferred, cancellation rates, and HTTP status distributions so you spot regressions before users complain.

Most Android networking bugs aren't HTTP bugs at all. They're lifecycle bugs where an abandoned coroutine updates a screen the user already left.

Run a quick checkpoint on a physical device or emulator: trigger a search on a throttled connection, rotate the phone while Loading is visible, and confirm that exactly one network call fires and its response renders cleanly after rotation.

Handling HTTP Errors, Timeouts and Expired Tokens

Reliable error handling starts with HTTP semantics rather than ad-hoc if/else blocks. RFC 9110 defines HTTP status codes as three-digit integers from 100 through 599, assigns the 2xx class to successful requests (including 200 OK and 201 Created), separates methods such as GET, POST, PUT, and DELETE, and draws a clean boundary between 4xx client errors (like 400 Bad Request and 404 Not Found) and 5xx server failures.

Map every status code and transport failure to a deterministic client action before writing retry logic.

Status code Meaning Client action
200 OK Request succeeded Parse the body and show Content or Empty
201 Created A new resource was created Store the returned ID and confirm to the user
202 Accepted Accepted but still processing Poll the job status endpoint and show progress
400 Bad Request Malformed query or body Show an input error and do not retry
401 Unauthorized Missing or expired token Refresh the token once, then retry or sign out
404 Not Found Requested resource does not exist Show the Empty state and do not retry
5xx Server error Backend failure Retry GET with backoff, capped at three attempts
No response (timeout or no connection) Request never completed Retry GET with backoff, then show Network error

Retry Rules and Single-Flight Token Refresh

Blindly retrying every failed call creates duplicate uploads and hammers struggling servers. Apply strict method-aware rules instead:

  • Retry only safe GET requests on timeouts, dropped sockets, and 5xx errors. Use exponential backoff with random jitter (for example, 1 s, 2 s, and 4 s delays) capped at three attempts so thousands of reconnecting phones don't synchronize into a thundering herd.
  • Never auto-retry a media upload POST unless your backend enforces an idempotency key header. If the server saved the video clip right before the phone lost Wi-Fi on the acknowledgment, retrying blindly creates duplicate files and wasted processing jobs.
  • Serialize 401 Unauthorized refreshes behind a Mutex. When a screen fires five parallel requests with an expired JWT, only the first coroutine should hit the refresh endpoint while the others wait on the lock. Once the fresh token lands, retry the original request once; if the refresh fails, clear stored credentials and route the user to sign in.
  • Respect 429 Too Many Requests headers. Read the Retry-After response header and suspend for that duration instead of guessing a delay.

Exception mapping needs the same precision. Convert SocketTimeoutException and UnknownHostException into a domain Network failure with canRetry = true. Convert JSON converter exceptions (SerializationException or JsonDataException) into Unknown with canRetry = false, and log only the HTTP status code and response byte length, never the raw response body.

Production Traps That Break Naive Parsers

Even experienced teams get blindsided by three HTTP edge cases in the wild:

  • Error payloads wrapped inside 200 OK: Some gateways return status 200 with a JSON body containing "error": { ... } instead of a 4xx code. Validate required fields in your repository before returning Success.
  • Captive Wi-Fi portals returning HTML with 200 OK: Hotel and airport networks hijack HTTP traffic and serve a login webpage. Checking Content-Type: application/json before parsing catches this cleanly and maps it to a Network error instead of an unexplained crash.
  • Asynchronous 202 Accepted on uploads: Indexing long video and audio files doesn't finish inside a single HTTP round trip. Treat 202 Accepted as a signal to store the returned jobId and start polling getJobStatus(jobId) with backoff rather than telling the user the file is searchable right away.

Debugging note: Force a 401 Unauthorized in staging while firing three concurrent requests from your ViewModel. If your server logs show more than one token refresh call, your Mutex lock isn't guarding the refresh path properly.

Before moving on, verify two things against your staging server: every error category in the table above renders the exact user message and retry button state you expect, and a forced expired token refreshes exactly once.

Streaming Large Media Without Out-of-Memory Crashes

The single fastest way to crash an Android app is treating a 400 MB dashcam or CCTV clip like a JSON string by calling file.readBytes(). Loading a video into heap memory triggers an OutOfMemoryError on mid-range phones almost instantly. Instead, subclass OkHttp's RequestBody and stream bytes directly from ContentResolver.openInputStream(uri) or a FileChannel into the BufferedSink in small buffers (such as 8 KB or 64 KB).

Structure resilient uploads in four steps:

  1. Chunk large recordings into fixed-size segments and send each segment as a @Multipart part tagged with its byte offset and upload session ID.
  2. Persist the last confirmed byte offset locally (in Room or DataStore) after each 200 OK or 201 Created chunk response so a dropped tunnel connection resumes cleanly instead of restarting from byte zero.
  3. Hand background transfers to WorkManager with NetworkType.UNMETERED constraints as soon as the user leaves the screen, letting Android finish the sync reliably on Wi-Fi.
  4. Emit upload progress from bytes written to the sink, and wire the UI's Cancel button directly to call.cancel() on the active OkHttp call so the radio stops transmitting immediately.

Comparing Physical AI and Robotics against conventional Media Content apps (phones, smart glasses, GoPros, dashcams, and CCTV) highlights a sharp architectural divide. Mobile media apps primarily capture footage for human playback and review. Across both worlds, teams rely on timestamped Multimodal Video and Multimodal Audio retrieval rather than manual scrubbing:

  • Advertisement video edition: Editors locate specific product shots or on-camera actions across hours of raw studio footage in seconds.
  • DashCam: Fleet and consumer apps surface near-collisions, sudden braking, or road hazards without forcing drivers to replay full commutes.
  • CCTV and Video Surveillance: Operators narrow multi-camera recordings to a specific person, vehicle, siren, or time window.
  • Vision for Robotics and Audio for Robotics: Engineers pull the exact camera frames and acoustic signatures (such as alarms, impacts, or motor anomalies) surrounding a failed grasp or obstacle event.

Device Pain Points You Will Hit in Production

Real deployments rarely look like clean studio clips. Plan your client and upload pipeline around five recurring failure modes:

  • Wind and traffic noise on smart glasses: Open-air microphones saturate easily, so avoid compressing audio tracks too aggressively before upload.
  • GoPro files overwhelming cellular uplinks: High-bitrate action footage stalls over LTE; enforce Wi-Fi-only WorkManager queues by default with an explicit user override.
  • Audio and video timestamp drift: Long continuous clips from dashcams or edge cameras can drift out of sync across streams; preserve container timestamps and device clock offsets in your upload metadata.
  • Privacy and retention gates on CCTV: Raw site footage often requires consent checks, masking, or local retention windows before a single frame leaves the premises.
  • Intermittent factory and roadside connectivity: Robotics and vehicle systems cannot rely on constant cloud reachability, which drives edge-first recording with deferred REST synchronization.

Teams building camera-heavy apps often pair their custom UI with specialized visual video search tooling for mobile developers so they don't have to reinvent chunked streaming and progress tracking from scratch. Even if you keep everything in-house, notice what stays constant: your repository contract, sealed SearchUiState, and HTTP error mapper carry over unchanged. Only the streaming RequestBody and the WorkManager upload worker change.

Once you understand the moving parts of a production Android REST client, you face a practical engineering trade-off: maintain your own Retrofit and OkHttp stack from scratch, or start from a published native Kotlin SDK.

Custom Retrofit Client Versus a Published Kotlin SDK

Rolling your own Retrofit client makes sense when you own both the mobile app and a bespoke backend with custom authentication flows, unusual response envelopes, or strict zero-third-party-SDK rules. You control every interceptor, timeout, and retry branch, but you also own every future bug fix around multipart chunking, signed URLs, and cancellation.

Starting from a native SDK cuts integration time dramatically when you're connecting to an existing multimodal backend.
